# KNOWLEDGE-MAP：经验归集地图与蒸馏流程

> 回答一个问题：部署经验散落在 EB 协议、工作日志、LL 台账、标本 exe 里，
> 如何持续归集进本仓库，保证任何 Agent 拿到仓库就能复用全部避坑经验？

## 1. 知识的三态与去向

| 原始形态 | 性质 | 去向 |
|---|---|---|
| EB 协议条款（G40-G45 等） | 通用纪律，跨项目 | **蒸馏进 TROUBLESHOOTING/RUNBOOK 对应节**，仓库内不引用 EB 内部编号（外部读者无上下文），改用自足描述 |
| LL 台账（LL-47~50） | 项目级教训 | 同上，逐条映射进坑位表（已做：LL-47→P-03/04，LL-48→P-06/07/08，LL-49→P-11/12/13，LL-50→P-09） |
| 工作日志（每日 md） | 原始过程记录 | **不直接进仓库**（含内部路径/密钥风险）；周期性蒸馏成 RUNBOOK 更新或新 P 条目 |
| 标本 exe（CDP 变体等） | 二进制参考件 | **本体不进仓库**；萃取清单与萃取产物进 `specimens/`（registry.json + 事实规格文档） |
| 可运行代码（shim/gateway/工具） | 已验证实现 | 直接进 `tools/`，README 标注「以代码为准，文档可能滞后」 |

## 2. 仓库内的知识分层（Agent 检索顺序）

```
① docs/TROUBLESHOOTING.md   症状索引的坑位总目 ← 出错先查这里
② docs/RUNBOOKS/            按任务组织的操作序列（安装/CDP/批跑/图标）
③ docs/PROTOCOLS/           协议规格（图像协议、localStorage schema、
                            磁盘缓存布局、CDP 操纵面）
④ specimens/registry.json   二进制标本登记：哈希、萃取清单、访问策略
⑤ tools/ 源码               终极事实来源（文档与代码冲突时信代码）
```

设计原则：**Agent 按症状检索（①），按任务执行（②），按规格深挖（③④），
按代码兜底（⑤）**。每层不重复存储同一事实，坑位表只存「症状→指针」
级别的浓缩条目，细节留在 RUNBOOK/PROTOCOL。

## 3. 蒸馏流程（持续运营）

```
触发：每次部署/排障会话结束
  ↓
1. 新坑是否出现？
   是 → 按「症状/根因/正解/验证」四元组追加 TROUBLESHOOTING 表尾（P-xx 递增）
  ↓
2. 既有 RUNBOOK 是否失效？
   是 → 原地更新对应步骤，git commit 注明触发案例
  ↓
3. 标本是否需要新增萃取项？
   是 → 更新 specimens/registry.json 的 extraction_checklist
  ↓
4. 内部知识源（EB/LL）已更新？
   → 对照第 1 节映射表同步进仓库；内部编号不出仓库
```

## 4. 溯源规则

- 仓库内每条坑位/规格，在条目尾部以 `(src: 2026-11-07 会话, LL-49)` 形式
  留**内部溯源指针**（仅供维护者，外部读者可忽略）；
- 蒸馏时**剥离**：内部绝对路径、主机名、密钥、内部项目代号；
- 剥离后的事实必须自足：外部 Agent 无需任何内部上下文即可执行。

## 5. 标本 exe 的处理原则（重申）

逆向原则奔着**重构**去，因此标本的价值 = 可萃取的知识，不是比特本身：

1. 本体固化在本地/私有渠道（登记于 `specimens/registry.json`）；
2. `extraction_checklist` 列明 Agent 拿到合法副本后应解析出的全部事实
   （段表结构、invoke 契约、ACL 清单、配置 schema……）；
3. 萃取出的**文本规格**提交进仓库——这部分是干净可再分发的；
4. 公开仓库永远不出现原厂二进制、图标、商标资产。
